# 一键排障编排方案（七节点 StateGraph）

> 目标：把 `POST /api/ai_ops` 从「Supervisor 让 LLM 决定调 Planner / Executor」改成「显式 StateGraph 按代码流转」的七节点流水线：告警接入 → 根因分析 → 处置规划 → 风险分级 → 执行 → 验证 → 沉淀。触发方式保持手动一键；人工审批采用两段式（段 A 出报告并落库，L2 停下等审批；审批后另起段 B 执行）。

---

## 1. 范围与不变项

| 项 | 决定 |
|---|---|
| 触发 | 保持手动：前端「AI Ops」按钮 / 评测脚本 `POST /api/ai_ops`。不接 Alertmanager webhook |
| 对外协议 | `/api/ai_ops` 仍是 SSE；`type=content / done / error` 语义不变，报告仍以 `# 告警分析报告` 开头。评测脚本（只认 content/done/error）无需改动 |
| 新增 SSE 类型 | `stage`（节点进度）、`approval`（待审批卡）、`incident`（终态摘要）。data 为 JSON 字串；旧客户端忽略未知类型 |
| LLM 出现的位置 | 只在 ② 根因分析（ReactAgent）与 ⑦ 沉淀（复用 `ExperienceService` 的提炼）；其余节点均为确定性 Java |
| 经验飞轮 | 复用 `ExperienceService.recall / selectAdoptedExpIds / distillAndStore` 与 `ExperienceLifecycleService.feedback`，不改经验库逻辑 |
| 删除 | `AiOpsService`（Supervisor / Planner / Executor 三套提示词与三级报告提取） |
| 不做 | 通用 shell 执行；自愈只能从 playbook 目录中选，不能自由生成命令 |

## 2. 编排图

```
段 A（/api/ai_ops 一次请求内完成）
START → intake → rca → plan → risk ─┬─ AUTO_EXECUTE ──→ execute → verify → distill → END
                                    ├─ NO_ACTION ─────────────────────────→ distill → END
                                    └─ PENDING_APPROVAL → END（incident.status=PENDING_APPROVAL，白板落库）

段 B（POST /api/incidents/{id}/approve 触发，从库中读回白板）
START → execute → verify → distill → END
```

实现：`com.alibaba.cloud.ai.graph.StateGraph`（已在依赖 `spring-ai-alibaba-graph-core 1.1.0.0-RC2` 中，API 已用 javap 核对）。节点为 `NodeAction`，条件边为 `EdgeAction`。两个 `CompiledGraph` 共享同一批节点 Bean。

不使用框架的 `interruptBefore` + checkpoint：RC2 之后版本仍有 resume 丢 state（#4519）与 checkpointId 复用（#4708）的问题，且 `MemorySaver` 重启即丢。两段式不依赖框架状态恢复，白板落 MySQL。

## 3. 白板（共享状态）

白板 = `OverAllState` 中一组**有类型**的 key。每个节点只读写约定的 key。所有值为 Jackson 可序列化 POJO，段 A 结束时整张白板序列化进 `incident.state_json`，段 B 启动时反序列化回 `Map<String,Object>` 作为图输入。

| key | 类型 | 写入者 | 说明 |
|---|---|---|---|
| `incident_id` | String | 编排服务 | UUID，也是 SSE 进度总线的路由键 |
| `provider` | String | 编排服务 | 模型供应商（deepseek / dashscope） |
| `incident` | `Incident` | ① intake | 去重后的 firing 告警、根组件、症状组件、告警快照 JSON、召回查询 |
| `recalled_experience` | `List<RecalledExperience>` | ① intake | 预召回经验（供 ⑦ 判定采纳与回写） |
| `experience_block` | String | ① intake | 注入 RCA 提示词的经验块 |
| `rca_conclusion` | `RcaConclusion` | ② rca | root_cause / confidence / root_component / evidence / adopted_exp_ids / proposed_playbooks |
| `report_markdown` | String | ② rca | 《告警分析报告》正文（不含 JSON 尾块） |
| `remediation_plan` | `RemediationPlan` | ③ plan | 选中的 playbook、目标、命令、回滚、预期、前置检查结果、dry-run 文本 |
| `risk_decision` | `RiskDecision` | ④ risk | level L0/L1/L2、score、reasons、decision（AUTO_EXECUTE / PENDING_APPROVAL / NO_ACTION） |
| `execution_result` | `ExecutionResult` | ⑤ execute | 每条命令的退出码 / stdout / stderr（截断）、是否模拟执行 |
| `verification_result` | `VerificationResult` | ⑥ verify | resolved、耗时、剩余 firing、验证方式 |
| `distill_result` | `DistillResult` | ⑦ distill | 沉淀的 expId、采纳并回写的 expId、是否 grounded |
| `audit_trail` | `List<String>`（Append） | 各节点 | 人可读的节点事件，同步写 `incident_audit` |

原始工具输出（CLS 日志原文、告警 JSON 全文）不进白板正文；`Incident.alertsSnapshot` 只保留精简告警列表。

## 4. 节点定义

### ① intake（确定性）

- `QueryMetricsTools.queryPrometheusAlerts()` 取快照（含 8 次重试）→ `extractFiringAlerts` 去重
- 按拓扑归并：`alert → component`（配置 `alert-components`；缺省按 alertname / service / instance 关键词匹配）；组件 c 若其任一（传递）依赖也在告警集合内则为「症状」，否则为「根候选」
- 预召回：`toExperienceRecallQuery` → `experienceService.recall` → `formatExperienceBlock`
- 写 `incident`、`recalled_experience`、`experience_block`；`incident` 表插入 `ANALYZING`

### ② rca（LLM）

- 引擎由 `aiops.orchestration.rca.engine` 选择：
  - `plan-execute`（默认）：Planner / Executor / Supervisor 三个 Agent 做「规划→执行→再规划」闭环（与旧 `AiOpsService` 同源）。Supervisor 内层 `StateGraph` 对外层七节点图是**黑盒**：`invoke(task)` 进、报告文本出，不共用白板；`recursion-limit` 限步数，`timeout-seconds` 限墙钟，等待期间每 `heartbeat-seconds` 向 SSE 推一行心跳
  - `react`：单个 `ReactAgent` 一次跑完
- 工具与现状一致：时间、知识库、Prometheus、`loadSkill` + CLS MCP
- 输入：告警快照、拓扑归并结果（根候选优先）、经验块、playbook 目录（id / 标题 / 适用告警 / 风险）
- plan-execute 的报告提取沿用三级链：`planner_plan` 是 Markdown → 直接用；仍是 `{"decision":"FINISH","finalReport":…}` → 抽报告字段；否则扫描内层状态取含「告警分析报告」的文本。残留的调度 JSON（含 `decision` 而无 `root_cause` 的 ```json 块）从正文剔除
- 输出契约：先按现有模板输出 Markdown《告警分析报告》，最后附一个 ```json 块：

```json
{
  "root_cause": "…", "confidence": 0.0, "root_component": "mysql",
  "affected_alerts": ["MySQLDown"], "evidence": ["…"],
  "adopted_exp_ids": ["<uuid>"],
  "proposed_playbooks": [{"playbook_id": "start-mysql-container", "target": "mysql", "reason": "…"}]
}
```

- 解析：取最后一个含 `root_cause` 的 ```json 块 → `RcaConclusion`；正文去掉该块存 `report_markdown`
- 结论缺失的兜底（`extract-conclusion-with-llm=true`）：再用一次**无工具**的 LLM 调用，只读报告 + 拓扑 + playbook 目录，输出结论 JSON（`parseNote=extracted_from_report`）。仍失败则 `parsed=false`：③ 只按告警名 / 关键词选 playbook，④ 按 L2 处理。提议的 playbook 不在目录中的一律丢弃
- 提示词保留现有硬约束：禁止编造；Prometheus 连接失败 ≠ 无告警；CLS 0 条 ≠ 无故障；查 CLS 前 `loadSkill(cls-log-query)`；采纳经验须写「采用经验: <expId>」

### ③ plan（确定性）

- 候选顺序：RCA 提议的 playbook（须在目录中且 `component` 与根候选一致）→ 目录中 `match-alerts` 命中 firing 告警名的 → 目录中 `match-keywords` 命中报告文本的（如 `Too many connections`）
- 前置检查：SSH 执行 `precondition`，stdout 匹配 `precondition-expect` 才通过（例：容器状态必须是 `exited`，若已 `running` 则「启动容器」无意义）。`remediation.enabled=false` 时跳过检查并标记未检查
- 输出 `RemediationPlan`；无候选则 `empty=true` 并写原因

### ④ risk（确定性）

- 基础等级取 playbook 的 `risk`；`rca_conclusion.confidence < min-confidence-for-auto` → 提升到 L2
- 前置检查失败 → `NO_ACTION`；熔断器打开（同 playbook + 目标 1 小时内执行次数 ≥ 上限）→ `NO_ACTION`
- 等级 ∈ `auto-execute-levels`（默认 L0、L1）→ `AUTO_EXECUTE`；否则 `PENDING_APPROVAL`
- `score` 仅用于展示：L0=10 / L1=40 / L2=70，加 `(1-confidence)×30`，高关键度组件 +10
- 条件边按 `decision` 路由；`PENDING_APPROVAL` 时把白板落库、状态置 `PENDING_APPROVAL`、推 `approval` SSE 后结束段 A

### ⑤ execute（确定性）

- `SshCommandRunner`（JSch）逐条执行 `commands`，单条超时可配，退出码非 0 即停止
- `remediation.enabled=false` → 不连 SSH，返回 `simulated=true` 的结果（dry-run）
- 每条命令写 `incident_action`（供熔断计数与审计）

### ⑥ verify（确定性）

- 有 firing 告警名：每 `interval-seconds` 轮询 Prometheus，直到这些告警全部不再 firing 或超时 `timeout-seconds`
- 无告警名（如 fw-05）：执行 playbook 的 `verify-command`，stdout 匹配 `verify-expect`
- 两者皆无 → `method=none`，`resolved=false`
- 状态：resolved → `RESOLVED`；否则 `UNVERIFIED`

### ⑦ distill（复用现有闭环）

- 报告 + 「自动处置记录」（计划 / 执行 / 验证摘要）拼成最终文本
- `selectAdoptedExpIds`；grounded = 报告覆盖 firing 告警名（与现状一致）；grounded 正反馈，否则负反馈且不沉淀
- `distillAndStore("aiops-<incidentId>", "自动告警分析任务", text, false)`。验证通过时文本明确写「告警已 resolved」，现有 `verifyMetricRecovery` 也会看到告警消失 → 直接进 strong

## 5. 持久化

```sql
incident        (id PK, status, provider, firing_names, root_components, risk_level, decision,
                 report_md, state_json, error, approved_by, approve_comment, created_at, updated_at)
incident_audit  (id, incident_id, node, event, detail, created_at)
incident_action (id, incident_id, playbook_id, target, command, exit_code, simulated, created_at)
```

状态机：`ANALYZING → PENDING_APPROVAL | EXECUTING | NO_ACTION | FAILED`；`PENDING_APPROVAL → EXECUTING | REJECTED`；`EXECUTING → VERIFYING → RESOLVED | UNVERIFIED`。

## 6. 接口

| 接口 | 说明 |
|---|---|
| `POST /api/ai_ops`（SSE） | 段 A。`content` 推节点进度行与最终报告；`stage` 推节点事件；L2 时推 `approval`；结束推 `incident` 与 `done` |
| `GET /api/incidents?status=PENDING_APPROVAL` | 待审批列表 |
| `GET /api/incidents/{id}` | 详情（状态、报告、计划、风险、执行、验证、审计） |
| `POST /api/incidents/{id}/approve`（SSE） | body `{approver, comment}`；从库读回白板起段 B，流式推执行 / 验证 / 沉淀进度 |
| `POST /api/incidents/{id}/reject` | body `{approver, comment}`；状态 `REJECTED`，写审计 |

`approval` 事件 data：

```json
{"incidentId":"…","riskLevel":"L2","score":78,"reasons":["…"],
 "plan":{"playbookId":"mysql-raise-max-connections","title":"…","target":"mysql",
         "commands":["…"],"rollback":"…","expectedEffect":"…","dryRun":"…"}}
```

## 7. 配置（`aiops.orchestration.*`）

```yaml
aiops:
  orchestration:
    rca:
      engine: plan-execute           # plan-execute | react
      recursion-limit: 40            # 内层 Supervisor 图步数上限
      timeout-seconds: 480           # RCA 墙钟上限（SSE 总超时 600s）
      heartbeat-seconds: 30
      extract-conclusion-with-llm: true
    remediation:
      enabled: false                 # false = 只 dry-run，不连 SSH
      auto-execute-levels: [L0, L1]
      min-confidence-for-auto: 0.7
      ssh: { host, port, username, password, connect-timeout-ms, command-timeout-ms }
      circuit-breaker: { max-executions-per-hour: 2 }
      verify: { timeout-seconds: 150, interval-seconds: 15 }
    topology:
      alert-components: { MySQLDown: mysql, RedisDown: rabbitmq… }
      components:
        mysql:   { criticality: high, depends-on: [] }
        course:  { criticality: medium, depends-on: [mysql, redis, rabbitmq, nacos], aliases: [course-service, tj-course] }
        gateway: { criticality: high, depends-on: [nacos, course, auth, …] }
    playbooks:
      - id: start-mysql-container
        title: 启动已停止的 MySQL 容器
        component: mysql
        match-alerts: [MySQLDown]
        risk: L1
        precondition: "docker inspect -f '{{.State.Status}}' mysql"
        precondition-expect: "^(exited|created|dead)$"
        commands: ["docker start mysql"]
        verify-command: "docker inspect -f '{{.State.Status}}' mysql"
        verify-expect: "^running$"
        rollback: "docker stop mysql"
        expected-effect: "mysql_up 恢复为 1，MySQLDown 在 2 分钟内 resolved"
      - …redis / rabbitmq(mq) / course(tj-course) 同型，均 L1
      - id: mysql-raise-max-connections
        risk: L2
        match-keywords: ["Too many connections", "max_connections", "连接打满", "连接耗尽"]
        precondition: "docker inspect -f '{{.State.Status}}' mysql"
        precondition-expect: "^running$"
        commands: ["docker exec mysql sh -c 'mysql -uroot -p\"$MYSQL_ROOT_PASSWORD\" -e \"SET GLOBAL max_connections=500\"'"]
        rollback: "SET GLOBAL max_connections=151"
```

安全约束：命令只来自 playbook 目录；SSH 凭据只在 `application.yml`（已 gitignore）；输出截断 2000 字符；`remediation.enabled=false` 为示例配置默认值。

## 8. 前端

- `content` 累积渲染报告（不变）
- `stage` 事件收进「查看详细步骤」折叠区
- `approval` 事件在报告下方渲染审批卡：风险等级 / 分数 / 原因 / dry-run 命令 / 回滚 / 预期，按钮「批准执行」「拒绝」
- 批准：`POST /api/incidents/{id}/approve` 读 SSE，把执行 / 验证 / 沉淀进度追加到同一条消息；拒绝：`POST …/reject` 后卡片置灰

## 10. 验收

1. `mvn -q compile` 通过；启动后 `/api/ai_ops` 在无告警时仍能出报告并 `done`
2. fw-01（停 MySQL）：段 A 报告命中 MySQLDown；risk=L1 → 自动 `docker start mysql`；verify 在 150 秒内看到 MySQLDown 消失；`experience_meta` 新增 strong 或合并更新
3. fw-05（连接打满）：无 firing 告警，报告命中「Too many connections」；playbook 命中 L2 → `PENDING_APPROVAL`；前端出现审批卡；批准后段 B 执行、`verify-command` 通过
4. `remediation.enabled=false` 时全流程只 dry-run，`incident_action.simulated=1`
5. 现有评测脚本 `run_flywheel_eval_single.py` 不改即可跑通（只读 content/done/error）
