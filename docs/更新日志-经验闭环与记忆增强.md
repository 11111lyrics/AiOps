# 更新日志 - 经验闭环与记忆增强

> 日期：2026-08-11  
> 功能：经验召回 recency 因子 + 经验合并更新 + Agent 主动记忆工具 + 弱触发经验召回与晋升 + AIOps 失败路径补齐 + 会话生命周期同步 + 上传契约修复

---

## 一、为什么要做这批改动？

对整个项目做了一次"逻辑闭环"审查（对话记忆链 / AIOps 链 / RAG 链 / 前后端契约四条线），确认正向路径都能走通，但存在若干断链：

| 断链 | 影响 |
|------|------|
| 弱触发经验写入 `experience_temp` 后无任何召回路径 | 经验"存而不用"，AIOps 沉淀的经验大量流入死存储 |
| 经验召回只看 相似度×置信度，无时间因子 | 上周刚处理过的同类故障与一年前的经验权重相同 |
| 经验只能新增+归档删除，无法原地更新 | 同一故障出现新解法时产生近似重复条目 |
| 经验沉淀只有对话结束后的固定异步流程 | 用户说"记住这个结论"时 Agent 无能为力 |
| AIOps 报告提取只读 `planner_plan` 一个 key | LLM 输出格式稍偏则报告丢失，且评分/沉淀整体跳过 |
| AIOps 失败路径无负反馈 | 无效经验的置信度永远不会因失败而下调 |
| 前端删会话只删 localStorage、后端不回传 sessionId | 前后端会话数据永久分叉 |
| 上传 `.markdown` 被拒、>1MB 文件 413 | 前端放行、后端拒绝的契约错位 |

## 二、经验体系改动

### 2.1 召回评分引入 recency 时间因子

```
finalScore = 相似度 × 置信度 × recency
recency    = floor + (1 - floor) × 0.5^(距上次使用天数 / 半衰期)
```

- 参考时间优先 `last_used`（无则 `created_at`）；命中召回即刷新 `last_used`，常用经验自增强
- 默认半衰期 14 天、下限 0.3（老经验降权但不归零）
- 位置：`ExperienceService.recallFactor/loadMeta`（召回 L3 层）

### 2.2 经验可更新（Mem0 式合并）

新提炼经验与已有经验余弦相似度 ≥ `update-threshold`（默认 0.85）且问题已闭环时，不再新增近似重复，而是：

```
LLM 合并新旧两条经验（症状/方案取并集，根因以更具体者为准，置信度取高值）
→ 同 expId 删除重插 Milvus（向量随之刷新）
→ MySQL 元数据保留使用计数，置信度取较大值
```

合并失败保留旧经验，不影响主流程。原 `isNewPattern` 重构为 `findTopMatch`，一次 top-1 检索同时服务"新模式判定"与"合并更新判定"。

### 2.3 弱触发经验：从死存储到全生命周期闭环

**改动前**：弱经验写 `experience_temp`（MySQL），只有 INSERT 和 TTL 删除，永不参与召回。

**改动后**：弱经验与强经验同路径入 Milvus + `experience_meta`，差别仅在：

| 维度 | strong | weak |
|------|--------|------|
| metadata.tier | strong | weak |
| 初始置信度 | 提炼置信度 | 提炼置信度 × `initial-factor`（0.7） |
| 召回排序 | 正常 | 因置信度低自然靠后 |
| 提示词标注 | 【候选经验N｜可信度x.xx】 | 【候选经验N｜可信度x.xx｜待验证】 |

生命周期闭环：**评分成功 → 置信度爬升至 `promote-confidence`（0.7）→ 自动晋升 strong；长期不用 → 衰减至 0.2 以下 → 归档删除**。`experience_temp` 表停止写入，TTL 清理保留用于排空存量。

### 2.4 Agent 主动记忆工具（MemGPT 式）

新增 `AgentMemoryTools`，注册进 ReactAgent：

- **saveMemory(title, content)**：用户说"记住……"或 Agent 确认重要可复用结论时主动保存（`source=agent`，置信度 0.7）；保存前做相似度检查，高相似时走合并更新避免重复记忆
- **searchMemory(query)**：自动注入的经验不足时，Agent 主动检索长期记忆，返回带 expId 与加权分数的结果

system prompt 中加了使用指引，并明确"不要保存寒暄或未经验证的猜测"。

## 三、AIOps 失败路径补齐

### 3.1 报告提取三级兜底链

`AiOpsService.extractFinalReport` 从"只读 `planner_plan`"改为：

1. `planner_plan` 为 Markdown 报告 → 直接使用
2. `planner_plan` 为 JSON → 尝试提取 `finalReport / final_report / report / content` 字段
3. 兜底扫描整个编排状态：优先含"告警分析报告/告警处理详情"标题的文本，否则取最长的实质性输出（≥300 字符）

### 3.2 失败负反馈

| 路径 | 行为 | 理由 |
|------|------|------|
| 编排无有效结果 | `feedbackBatch(recalledExpIds, false)` | 分析消费了经验但未产出 |
| 报告提取失败（含兜底） | 同上 | 同上 |
| 异常（网络/LLM 服务故障） | **不评分** | 基础设施故障不是经验的错，惩罚会误伤 |

## 四、会话生命周期同步

- `/api/chat` 响应体新增 `sessionId` 字段；流式接口 done 帧的 `data` 携带 sessionId（前端对 done 帧 data 不敏感，不破坏现有解析）——API 客户端不传 `Id` 时也能拿到服务端生成的会话 ID 续接对话
- 前端删除历史会话时同步调用 `POST /api/chat/clear`（尽力而为，失败不影响前端删除），后端连滚动摘要一起清理

## 七、配置说明

```yaml
experience:
  recall:
    recency:
      half-life-days: 14    # 距上次使用每过 14 天，时间因子衰减一半
      floor: 0.3            # 因子下限，老经验不会被完全压死
  distill:
    update-threshold: 0.85  # 与已有经验相似度达到该值时合并更新而非新增
  weak:
    initial-factor: 0.7     # 弱经验初始置信度 = 提炼置信度 × 该系数
    promote-confidence: 0.7 # 置信度达到该值后 weak 晋升为 strong

spring:
  servlet:
    multipart:
      max-file-size: 50MB
      max-request-size: 50MB

file:
  upload:
    allowed-extensions: txt,md,markdown,pdf,doc,docx
```

## 八、验证方法

### 8.1 recency 因子

对比一条近期使用过与一条长期未用的相似经验，召回排序应前者优先；日志可观察 `RecalledExperience.recencyFactor`。

### 8.2 经验合并更新

对同一故障模式先后完成两次排障对话，第二次日志应出现 `[更新] 与已有经验高度相似，已合并更新` 而非新增；Milvus 中经验条数不变、内容已合并。

### 8.3 弱经验召回与晋升

1. 制造一次"LLM 判已解决但指标复核未通过"的对话，日志出现 `[弱触发] 经验已沉淀至 Milvus(tier=weak, ...)`
2. 新会话问相似症状，注入块中出现 `｜待验证` 标注
3. 调用 `POST /api/experience/feedback` 成功评分数次后，日志出现 `弱经验已晋升为 strong`

### 8.4 Agent 主动记忆

对 Agent 说"记住：XX 告警先查 YY"，日志出现 `[Agent记忆] 已主动保存`；新会话问相关问题，Agent 可通过 searchMemory 或自动注入召回。

### 8.5 AIOps 失败负反馈

模拟报告生成失败（如断开 Prometheus），确认 `experience_meta` 中本次召回经验的 `confidence` 被下调。

### 8.6 会话同步

前端侧边栏删除一个会话，确认 MySQL `chat_message` / `chat_session_summary` 中该 session 记录被清除。

### 8.7 上传修复

上传一个 5MB 的 PDF 和一个 `.markdown` 文件，均应成功入库。
